Flex and Count

A school project that became a phone web app and an Android app.

Problem

Our finals project counted right-arm bicep curls from a laptop webcam, inside a Jupyter notebook pinned to old Python libraries. It worked for the demo. Nobody could use it at the gym.

What I built

Version 2 runs in the phone browser. The pose model runs on the device, so nothing is recorded or uploaded. It counts standing or preacher curls on the right arm, left arm, both, or auto, from the camera or from a recorded video you can trim. A swing check marks reps that aren't strict. Sets are logged by day and export as CSV. The Android app wraps the same web app, so web updates need no new APK.

Version 1 is still in the repo, untouched, with its original commit date and both authors credited.

How I worked with AI

  • I set the product rules: the goal is per side, version 1 keeps its history, and privacy stays on-device.
  • I tested on my iPhone 11 and sent screen recordings whenever reps were missed. Each recording became a replayable test: per-frame angles were captured, then counter settings were replayed against the clip before anything was pushed.
  • That loop found real problems. A seated preacher curl filmed from a low camera never reads past 150°, so the counter gained a relative-swing rule. A speed limit that looked safe was throwing out real, fast alternating curls.
  • The look and the logo were my calls. I refined the mark myself in Figma.

Result

A notebook that needed a laptop is now a link you can open on any phone, plus an Android download. The Android app has only been tested on an emulator so far; a real-phone test is next.

Time Log

A one-tap time audit I use every day, on iPhone, Mac and Android.

Download TimeLog.apk iOS / Web Repo

Tech
Single-file HTML, CSS and vanilla JavaScript, Firebase Auth, Cloud Firestore with per-user rules, service worker, Kotlin for the Android shell
Tested on
iPhone 11 (daily), iOS Simulator, Mac, Android phone
Status
Web v0.6.0 · Android 0.2.1 · 150+ commits · 50+ pull requests

Problem

I was juggling an internship, school, coaching, content and training, with no honest picture of where my hours went. Every tracker I tried needed too many taps to survive a normal day.

What I built

Tap a tile to start. Tap another to switch. If you forget, backdate with a chip. A Gaps tab walks you through unlogged time, and Week shows goals and totals. "Kasabay" tracks what runs alongside the main activity without counting the time twice. Logs sync in real time and keep working offline, or you can use it with no account at all. The Android app adds a pinned live-timer notification, a home screen widget and reminders.

How I worked with AI

  • I use it daily, so features come from friction I hit myself: the newest-log-wins overlap rule, trips that group back-to-back rides, per-day goals.
  • Changes go through feature branches and pull requests, and I check each one on my phone after the merge.
  • When logs started getting flattened, the cause turned out to be an old browser tab still running old code against the same account. The fix was proven with a two-tab test on a fake backend before it touched real data.
  • I chose Firebase for real-time sync and offline support, and accepted the trade-off of not practicing SQL here.

Result

In daily use since November 5, 2026. It is the app that finally showed me where my week goes.

Project · repo live

Supplement ops agent

An internal-tools demo: messy CSV in, clean data, SQL insights and AI agents out.

Repo Architecture

Tech
Google Apps Script, Sheets, Drive, BigQuery SQL, Gemini API with function calling and JSON output, n8n, a TypeScript MCP server, Looker Studio
Data
A fictional brand (Kalye Nutrition) and synthetic demo data only
Status
Repo public · ETL and the data steward agent running on Google · 64 tests passing

Problem

A small supplement brand sells on its website, Shopee, Lazada and in two stores. Every week someone merges CSV exports by hand, fixes broken rows, guesses what to reorder and writes the report. It eats hours, and bad data quietly turns into bad orders.

What I built

A CSV dropped into a Drive folder is validated and cleaned in Apps Script. Bad rows (duplicate orders, unknown SKUs, prices typed as text) are set aside with a reason, and every run is logged. Clean data goes to Sheets and a BigQuery copy, where SQL views compute days of cover, weekly KPIs and margins. Three Gemini agents read it through read-only tools: a data steward explains every rejected row in plain words, an inventory analyst suggests reorders, and a report writer drafts the weekly report. An MCP server lets Claude ask the same data questions, like "what runs out in two weeks?".

How I worked with AI

  • I set the rules: the model never does the math. Days of cover and order quantities are computed in code, and the agents only read, compare and explain.
  • Agents can't write. Every reorder suggestion is checked against the tool numbers and saved as Pending until a person approves it. Nothing is sent to a supplier.
  • The SQL runs twice: on BigQuery, and locally on DuckDB, where every SKU's numbers are cross-checked against the JavaScript tools. A test caught a SKU with a 35-day lead time being missed, so low stock now also means "runs out before the supplier can deliver".
  • Running it live, the Gemini model I planned on was closed to new keys and the next one was overloaded. The script now picks an available model, switches on errors and works in batches within Apps Script's time limit.
  • Secrets stay out of the repo: keys in Script Properties, a token on the Web App, and a secret scan before every commit.

Result

On 90 days of demo data it flags 5 SKUs to reorder and 1 dead stock, and finds that paydays bring about 82% more revenue than other days. The weekly report is estimated to drop from about two hours of manual work to a few minutes. Next: the weekly agents on a schedule, the Looker Studio dashboard and a demo video.
